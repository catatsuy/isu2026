# 画像本体のファイル移行

画像本体だけを `/home/isucon/image-files` に保存します。署名キー・画像の所有者・
削除状態・公開状態はDBで判定します。配信とエクスポートはDBのdata列を読みません。
DBの既存バイナリは復旧用に残し、新規画像はdata=NULLで保存します。

## 既存画像の書き出し

`cmd/export-images` をLinux向けにビルドし、各地域の
`/home/isucon/webapp/go/deploy/export-images` に配置します。
同じ場所に `export-images.sh` を配置し、サーバー上で次を実行します。

```sh
bash /home/isucon/webapp/go/deploy/export-images.sh
```

1件ずつストリームで読み、画像IDのSHA-256から決定したパスへ書き出します。
既存ファイルは内容が一致した場合のみ再利用し、最後にsyncを実行します。
全件処理が成功した場合だけ `.export-complete` を作成します。
途中で失敗した場合は同じコマンドで再実行できます。
稼働中の書き出しでは、開始時刻を控え、全アプリ切り替え後に同じコマンドへ
`--since 開始時刻（RFC3339）` を付けて差分を書き出します。

## アプリとnginxの設定

1. 共有DBで `image-files.sql` を適用し、dataのNOT NULL制約を解除します。
2. 各地域の `/home/isucon/.image-file-token` に32文字以上の同じランダム認証キーを
   所有者だけが読み取れるモードで配置します。このファイルを公開ディレクトリへ置かないでください。
3. systemdの環境変数 `ISUREAL_IMAGE_PEERS` に他地域のアプリURLをカンマ区切りで指定します。
   例：asiaのサーバーにはeuropeとamericaのURLを指定します。
   固定リージョンとルーターを経由する既存経路は変更しません。
4. 各地域のserverブロックへ `image-files.nginx.conf` を追加し、設定検証後にreloadします。
5. 全件書き出しの完了後、Goアプリを配置し、差分を書き出します。

画像ファイルは永続データです。従来のキャッシュと違い、削除しないでください。
新規画像はローカルのファイルと必要なディレクトリのfsync後にSaveが成功し、DBへ登録します。
他地域の成功応答は待ちません。成功時の複製保証は従来の「ローカル＋他地域1台」から
「ローカル1台」に変わります。複製前に保存元が利用不能になると、DBに情報があっても
画像を取得できません。保存元のディスクを失うと、未複製画像は復旧できない可能性があります。
他地域の画像ファイルが未配置の場合は、認証付きの内部HTTPでファイルから復旧します。
内部HTTPは時刻・メソッド・画像ID・本文ハッシュをHMACで検証します。
再起動や初期化でファイルは消しません。画像IDは不変で、DBで認可できる画像だけ配信します。
ロールバック時は旧アプリが新規data=NULL行を読めないため、そのまま旧版へ戻さないでください。
必要ならファイルからDBへの復元を先に行います。

## 非同期レプリケーション

`Save`はサイズとPeer設定を確認し、不変画像を書き込み、ファイルと必要なディレクトリを
fsyncします。続いて画像IDだけのジョブを
`ISUREAL_IMAGE_FILE_DIR/.replication/<shard>/<hash>`へ永続化します。
最後にスケジューラへ通知して成功を返します。ジョブの永続化失敗もローカル画像の保存失敗も
エラーになります。画像保存とジョブ登録の間でクラッシュした場合は、未参照の画像ファイルが
残る可能性がありますが、Saveは成功しておらず、呼び出し元のDB更新にも進んでいません。
成功を返した画像には必ず永続ジョブがあるため、再起動後に複製を再開できます。
ジョブへの書き込みでも既存のファイル保存処理を使い、異なる画像内容による上書きは許可しません。

アプリ起動時にスケジューラ1個とワーカー4個を起動します。要求ごとのgoroutineは作りません。
ディスク上のジョブを64件ずつ走査し、メモリには実行中の少数のIDと最大4画像だけを保持します。
全Peerへ既存のHMAC付きPUTを送り、各PUTのタイムアウトは15秒です。
要求コンテキストではなくワーカー専用コンテキストを使います。
全Peerが204を返したジョブだけ削除し、そのディレクトリもfsyncします。
失敗時はログを出し、1、2、4、8、16、32、60秒（上限）のバックオフ後に再試行します。
再試行では成功済みPeerにも重複PUTする場合があります。

待機中の再試行はワーカーを占有しません。次の試行時刻はジョブのmtime、バックオフ秒数は
同じディレクトリの`.retry-*`に記録します。これらは補助情報であり、クラッシュで失われても
再試行間隔がリセットされるだけです。永続化したジョブ本体は再起動後に自動走査されます。
ジョブ登録済みの画像ファイルが外部から失われた場合、画像のないジョブが残ることがあります。
その場合も破棄せず、ログとバックオフ付きで再試行し、画像が戻れば複製します。
ディスク上の待機ジョブ数と容量は監視が必要です。

SIGTERM/SIGINTではHTTPの終了処理後にワーカーをキャンセルし、終了を待ちます。
中断されたジョブは次回起動時に再開します。強制終了でも永続ジョブから再開できます。
同じ保存先で動作するレプリケーションスケジューラはGoプロセス1個を想定しています。

複製途中でも他地域は`Ensure`から保存元の認証付きGETで取得し、取得先でもfsyncします。
既存のsingleflight、応答HMAC検証、DBの閲覧権限確認は維持します。
画像・ジョブはinitializeで消さず、削除・公開範囲は引き続きDBが決定します。
初期データの書き出しや、既存画像の読み取り経路は変更しません。

ベンチマークでは投稿・プロフィール画像更新・RealMojiの応答時間（p50/p95/p99）、
DBロック保持時間、ローカルfsync時間、複製完了までの遅延、待機ジョブ数・最古ジョブの経過時間、
Peer別エラー数・再試行数、GETフォールバック率、goroutine数・メモリ・ディスクI/Oを確認します。
ジョブ永続化による追加fsyncも含めて比較してください。性能改善値は未測定です。
