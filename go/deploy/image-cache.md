# 画像ファイルキャッシュの適用

画像の原本とアップロード先は引き続きPostgreSQLです。各地域の最初の画像取得で
ローカルファイルを生成し、以後はGoによる署名・有効期限・削除状態の確認後、
X-Accel-Redirectでnginxに配信させます。エクスポートの読み取り先は変更しません。

## 適用順序

1. 共有DBに `image-cache.sql` を適用します。既存画像テーブルは変更しません。
2. 各地域でGoが書き込めてnginxが読み取れるキャッシュディレクトリを用意します。
   既定値は `/home/isucon/image-cache`、Goの環境変数は `ISUREAL_IMAGE_CACHE_DIR` です。
   nginxのaliasも同じ絶対パスに設定してください。親ディレクトリの通過権限も必要です。
3. 各地域の既存serverブロックに `image-cache.nginx.conf` を組み込み、
   nginxの設定検証を通して反映します。画像APIのproxy_cacheは有効にしません。
4. Goアプリを配置します。全地域で画像が取得でき、二度目にDBのdataを読まないこと、
   不正署名・期限切れ・削除済み画像が403になること、内部URIの直接取得が404になることを確認します。
5. initialize後の全地域での取得、再起動後の取得、Memories・エクスポートを検証します。

## 初期化と運用

initializeは従来のDBリセット後、共有DBの世代番号を増やします。
画像キャッシュのキーには世代・画像ID・作成日時を含めるため、全地域で旧世代が
使われなくなります。失効・削除状態はキャッシュせず、毎回DBで確認します。
SQLスクリプトだけで初期化する場合は、アプリのinitializeと同様に世代更新も必要です。

キャッシュファイルは再生成可能です。書き込み途中のファイルは配信せず、完成後にrenameします。
ディスク不足などの書き込み失敗はエラーとして返します。旧世代のファイルは自動削除しないため、
ディスク使用量を監視し、走行のない時間にキャッシュを回収してください。
配信中の削除はnginxの404を招くため、全地域のアプリとnginxの利用がない状態で行ってください。
DB原本は削除しません。キャッシュ領域を失ってもDBから再生成できます。

この変更はnginxとの組み合わせが必須です。Goへの直接アクセスでは画像本体を返しません。
ロールバックは従来のGoアプリに戻せば可能で、追加テーブルは残して構いません。
